Ticket: $ARGUMENTS
(If the argument has extra words after the key, e.g. "it is now fixed", use only the key as `<KEY>` below, and treat the rest as context from the user.)

The user approved the plain-language cases in `/prepare-ticket` (`.loop/<KEY>/cases.approved`, which carries the frozen UI cases and contract). Each case has a lane. **Logic** cases (listed on the `Logic case IDs:` line) get a Groovy harness written and locked *before* the build. **UI** cases (every other approved case) get their tests in two phases: **Phase A** (the ui-assert agent, before the build) writes complete specs and an UNBOUND page-object interface from `cases.approved` alone, locked as `ui.locked`; **Phase B** (test-author UI-BIND, after the build) only fills in page-object bodies. So no UI expected value can come from the implementation. A ticket may have either lane or both: skip the steps for a lane it doesn't have.

The gate (`loop-verify.sh`) runs `loop-ui-check.js` first once `ui.locked` exists (exit 4 `CHECK:` = the locked contract was changed; nothing ran), then the Logic harness (stops there if red), then Playwright. Exit 3 (`INFRA:`) means the gate could not run and is not a test result.
- **Jira access:** `node ~/.claude/scripts/jira.js <get|comment|edit-comment|transitions|transition> <KEY> ...`. If a call exits with JIRA_AUTH_EXPIRED, stop and ask the user to refresh `~/.jira-cookie` (see `/prepare-ticket`).
- **Jira comments:** one per phase; `edit-comment` the existing one when the phase is updated. Comment ids are in `.loop/<KEY>/`. The test-evidence comment is posted by the reviewer through `loop-evidence.js` (step 8), never written by hand.
- **Version control is SVN.** Nothing in this command commits: the user checks the change in manually.
- **Servers:** follow `~/.claude/loop/servers.md`. If the project has no row there, stop and ask for `/setup-project`. Populate, reloads, p2c and restarts need the user, or the user's explicit say-so in this conversation. The exception is the implementer subagent, which may run them itself on the project's host (`servers.md` rule 1). You and every other agent still need the user.
- **Enforcement:** the hook `~/.claude/hooks/protect-locked-tests.js` knows which agent is calling. No subagent writes a lock marker or `cases.approved`; the implementer never writes under `e2sc-ui_tests/tests/`; after `ui.locked` nobody writes `specs/`, and only test-author writes `pages/`; ui-assert reads only its inputs. Shell commands that name a lock file are blocked for everyone, including you, unless they are plain reads; so are deletes of a `.loop/<KEY>/` that holds `ui.locked`; only you run `loop-ui-check.js --lock/--bound/--heal`. Shell-command matching is best-effort: **`loop-ui-check.js` is the real enforcement**, and you run it before every test run and before the reviewer (the gate also runs it). Its `--jira` mode compares `ui.locked` with the sha256 posted to Jira at lock time, which catches a lock file replaced by a script the hook couldn't see.

1. **Check the approvals and find the stage.**
   - `.loop/<KEY>/cases.approved` and `intake.md` must exist; if not, tell the user to run `/prepare-ticket <KEY>`. If the ticket has UI cases, `cases.approved` must have the `## Approved UI cases (frozen)` and `## Contract (frozen)` sections; if not, go back to the approval step of `/prepare-ticket` to freeze them.
   - **Older tickets** locked with `tests.locked` (single-phase UI tests): keep the old flow for them: check the hashes it lists, and those in `logic.locked`, then go to step 6. The hook still protects them.
   - `ui.locked` exists: run `node ~/.claude/scripts/loop-ui-check.js <KEY>` and `--jira` (the sha256 posted to Jira must match; stop and show the user if either fails; exit 3 from `--jira` means Jira couldn't be read: refresh the cookie and re-run, don't skip it) and check `logic.locked`'s hashes. Then: no `first-pass.md` → step 3; `first-pass.md` but no `ui.bound` → step 4 (or step 3 if `contract-mismatch.md` is open); `ui.bound` → step 6.
   - No `ui.locked`: step 2 (or 2a/2b for whichever of `logic.locked`/`ui.locked` is missing).
2. **Health check first.** A quick read-only check of the target server: the key page loads and the log has no new errors. If it's broken, tell the user and stop.
2a. **Logic tests first** (only if `cases.approved` has a `Logic case IDs:` line and `logic.locked` doesn't exist). Delegate to test-author in **LOGIC mode** with `model: opus` (the harness and its stubs are the oracle for the build). It writes the Groovy harness under `e2sc-ui_tests/tests/logic/<KEY>/` from the approved Logic cases and their contract, and runs the gate: every case must be RED, because the code doesn't exist or is unchanged. A case that is already GREEN proves nothing: send it back.
   - If the gate reports `INFRA:` (ssh or Groovy), tell the user; set `LOGIC_SSH` to the project's e2sc host from servers.md.
   - Then `node ~/.claude/scripts/loop-check.js <KEY> --logic`, then `--logic --lock`. That writes `.loop/<KEY>/logic.locked`. Judge it: the counts match, each case has a discriminating check in `test-plan.md`.
   - For a ticket that was already built (a re-run or a retro-fit), the RED run can use the earlier SVN revision: stage `svn cat -r <rev before the change>` under the same relative path and run the gate with `LOGIC_SRC_ROOT` pointing at it.
2b. **UI assertions (Phase A)** (only if the ticket has UI cases and `ui.locked` doesn't exist). Delegate to the **ui-assert** agent (`model: opus`; it is the UI oracle) with the key. It reads only `cases.approved` and the page template, and writes `e2sc-ui_tests/tests/locked/<KEY>/specs/*.spec.ts`, `pages/*.ts` (every method body `unbound(...)`) and `test-plan.md`. Record its ID in `.loop/<KEY>/ui-assert.id`.
   - **CONTRACT_GAP:** a UI case lacks a named step, a literal expected value or a model ID. Show the user the gaps; their answer is a contract change (see "Contract change" below), so update `test-cases.md` and `cases.approved` and resume ui-assert.
   - **ASSERT_READY:** run the specs yourself: `bash ~/.claude/scripts/loop-verify.sh <KEY> --ui-only` (offline: the first step of every test throws UNBOUND, so the server isn't touched). Every test must fail with `UNBOUND`; the summary ends with the classification. A test that passes, fails with a syntax error, or fails on an assertion before its first step goes back to ui-assert (resume it with the classification lines) and is run again.
   - Lock: `node ~/.claude/scripts/loop-ui-check.js <KEY> --lock`. It refuses unless the last run is newer than the files and every UI test failed with UNBOUND, the case-to-test mapping is exact, `test-plan.md` has a discriminating check per case, and specs and pages pass the lint. It writes `.loop/<KEY>/ui.locked` (sha256 of `cases.approved`, each spec, the page-object public signatures, the `expect()` counts, and every file outside `pages/` plus the shared helpers they import) and prints the sha256 of `ui.locked`.
   - **Post the lock to Jira:** a comment (one for this phase) with the UI case IDs and the spec file names, saying the UI assertions were written from the approved cases before the build, and the hash on a line of its own in exactly this form (`loop-ui-check.js --jira` parses it): `ui.locked sha256: <64 hex>`. Record the comment id. This is the out-of-band copy of the lock: `--jira` compares against it.
3. **First pass.** Delegate to the implementer in **FIRST PASS mode**, giving it the host from servers.md and, if one exists, the previous `handover.md` (a re-run of a STUCK first pass) or the open `contract-mismatch.md` (a fix, see step 4). **Model:** always pass `model: opus` (Opus 5.5), for Logic and UI-only tickets alike. A resumed implementer keeps the model it started with, so start a fresh one if it began on another model. It builds every approved case from the contract in `intake.md` and `cases.approved`, reloads, checks health, writes `first-pass.md` and reports FIRST_PASS_DONE. For Logic cases the gate is the locked harness and it must be GREEN before FIRST_PASS_DONE. If it reports STUCK, go to step 7.
4. **Bind the UI page objects (Phase B).** Skip if the ticket has no UI cases. Run `node ~/.claude/scripts/loop-ui-check.js <KEY>` first. Delegate to test-author in **UI-BIND mode** (`model: sonnet`, the agent default): SendMessage to the ID in `.loop/<KEY>/test-author.id` if it can still be resumed (same session), otherwise a fresh agent. It fills in page-object method bodies only (locators, clicks, navigation, waits) from the recordings and `INDEX.md`, and must not read `first-pass.md`, `svn diff` or the implementer's files. A UI wiring case for a Logic criterion needs its named record or fixture: check it exists before delegating.
   - **NEEDS_RECORDING:** show the user each flow in `.loop/<KEY>/recording-requests.md`: its name, the steps, what to assert, and the command `node ~/.claude/scripts/loop-record.js <KEY> <flow>` (it launches codegen, never overwrites an earlier recording, and checks the result when the browser closes). You may launch it in the background if asked.
   - Check each recording with `node ~/.claude/scripts/loop-record.js <KEY> <flow> --check`. It fails if the file is missing or empty, has no assertion, doesn't end on one (stops before the result screen), or its login step types something other than a username.
   - **If a screen or part of a flow is unknown, or a recording stops short, ask for another codegen recording. Don't discover it by trial runs:** they are slow on the shared server, and one trial run once took 40+ minutes. Say where the last recording stopped and what to continue with (click, wait, assert), with a new command and its own `--output` file.
   - Only if the user says to fill a small gap by script: delegate a throwaway spec in `tests/_discovery/` to a general-purpose subagent (`model: sonnet`) with a budget of at most 6 trial runs or 10 minutes, one line per trial with its duration in `.loop/<KEY>/discovery-progress.md`. It writes the steps and locators to `.loop/<KEY>/discovery-<flow>.md` and replies with that path and whether it succeeded. Queue extra scope as a second task.
   - Resume test-author (SendMessage) with the recordings and any fixtures. Check user-supplied fixtures first (e.g. SLSRPT files: field count and index positions against the transform) and confirm any mismatch.
   - **CONTRACT_MISMATCH** (a step can't be bound: missing, extra or reordered in the UI, or an asserted element differs in place, model ID or control): never let test-author resolve it by rebinding or rewriting. Show the user `contract-mismatch.md` and ask which way to go.
     - **Fix the build:** leave `contract-mismatch.md` in place and go to step 3. The implementer changes only what it lists, reloads, updates `first-pass.md` and reports FIRST_PASS_DONE. Then rename the file to `contract-mismatch-<n>.md` (closed) and resume test-author at step 4.
     - **Change the contract:** see "Contract change" below.
   - **TESTS_READY:** test-author ran the gate once. Read the classification at the end of `last-verify-summary.txt`:
     - `UNBOUND` or `BINDING` left: resume test-author once with those lines (it is binding work); if they remain, show the user.
     - `ASSERTION`: a defect. It goes to the implementer in step 6 with the tests unchanged.
     - **A failure the build evidence contradicts.** If an ASSERTION failure conflicts with what `first-pass.md` or `iterations.md` records (the implementer saw the same flow work), don't send it to the implementer yet. test-author can't read those files, so only you can see the conflict. Resume test-author once, without telling it the implementer's result, to check the failing step's binding on a freshly opened page. If it was a binding problem, it fixes the page method (no spec change). If it still fails, it is a behaviour failure.
5. **Record the binding.** Run `node ~/.claude/scripts/loop-ui-check.js <KEY>`, then `--bound`. `--bound` refuses while any method is unbound or any failure is UNBOUND, BINDING or OTHER; it writes `.loop/<KEY>/ui.bound` with a hash of every page-member body. From here any change to `pages/` goes through healing.
   - **Reserved: sabotage check (Phase B).** Not implemented yet. When it is, it runs here, on the bound tests, before step 6.
   - Edit the UI lock's Jira comment to add the binding result (pass/fail counts), one line.
6. **Iterate to green.** If the gate is already GREEN, go to step 8. Otherwise delegate to the implementer in **ITERATE mode** with the host, the budget (3 iterations from the binding; the first pass doesn't count) and, on a re-run, the previous `handover.md`. Same model rule as step 3. Run `node ~/.claude/scripts/loop-ui-check.js <KEY>` before each gate run you make; the gate runs it too, and exit 4 (`CHECK:`) is never the implementer's to fix: stop and show the user.
   - **INFRA doesn't use the budget.** `INFRA:` (exit 3) or a navigation or login timeout before any assertion is infrastructure, not a failing test: one retry, then tell the user with the evidence. Don't count it as an iteration or let the implementer change code for it.
   - **NEEDS_BINDING from the implementer** (the gate's only failures are `BINDING` or `UNBOUND`): route it to test-author in **UI-BIND** mode, never back to the implementer, and **don't count it**: the iteration in which the implementer returned NEEDS_BINDING is not one of the 3, and the implementer is resumed afterwards with the same remaining budget. With `ui.bound` present it is a heal (next bullet); without it, the binding is unfinished: resume test-author at step 4, then step 5.
   - **What counts as BINDING** (`--classify`): a locator that resolves to nothing (`element(s) not found`, or a timeout while waiting for the locator), whether it fails inside a page method or in a spec `expect` on a query method, and the failing locator does **not** use the method's contract model ID. If the failing locator already targets the contract model ID, the element the contract names isn't in the DOM: that is `ASSERTION` (a defect for the implementer), never a heal. A value that was found but differs is `ASSERTION`.
   - **Healing after the binding** (a `BINDING` failure once `ui.bound` exists; `--classify` has written `heal-request.json`): no need to ask the user. Resume test-author in UI-BIND mode with "heal" and the heal request. It changes only those methods (and private helpers of the same class), **re-binding by the contract model ID** in each method's doc comment, and replies HEALED. Then run `node ~/.claude/scripts/loop-ui-check.js <KEY> --heal`: it refuses a healed method that doesn't locate by its model ID, checks the change is limited to the failing methods, logs it to `healing.log` and `iterations.md`, and updates `ui.bound`. Exit 5 (`STOP_ASK`, the same method healed twice or more than 3 members changed): stop and ask the user. A healing doesn't count as an implementer iteration.
   - **Any change to an assertion** (a spec, an expected value, a signature) stops and comes to the user. There is no amendment path inside the loop for specs: it is a contract change.
7. **If STUCK:**
   - **NEEDS_SERVER_ACTION:** show the user the exact commands from `handover.md`. If they run them, check the result read-only (restart time, log errors, PCMM result, deployed files) and resume the implementer. If they tell you to run them, run exactly those and stop at the first failure.
   - **Otherwise:** post `handover.md` to Jira (edit the existing handover comment on the same run), leave the ticket in "Fix Required", write `.loop/<KEY>/run-summary.json` with outcome "escalated", and tell the user, with any broken shared server first.
8. **If GREEN:** run `node ~/.claude/scripts/loop-ui-check.js <KEY>` and `node ~/.claude/scripts/loop-ui-check.js <KEY> --jira`, and re-run `bash ~/.claude/scripts/loop-verify.sh <KEY>` yourself to confirm. Save both check outputs to `.loop/<KEY>/ui-check-review.txt`. A `--jira` failure (the lock file differs from the hash posted at lock time) stops the run: show the user. Exit 3 (Jira unreachable) is not a pass: refresh the cookie and re-run it before the reviewer.
   - If yours isn't green, find out why first: a behaviour assertion, or navigation or timing before any assertion? Look at the screenshots. Flaky navigation is a harness problem: take the evidence to the user (which tests failed in which runs) and offer a re-run.
   - Once confirmed, delegate to the reviewer. **Model:** `opus` for a ticket with Logic cases (full review), `sonnet` for a UI-only ticket (the reviewer's checklist pass). Tell it to read `ui.locked`, `ui-check-review.txt`, `ui.bound` and `healing.log`, and that on a non-BLOCK verdict it posts the test evidence as its last step (`node ~/.claude/scripts/loop-evidence.js <KEY> --verdict <V> --post`, built from this final gate run; pass any env the gate needed, e.g. `LOGIC_SSH`). Record the evidence comment id it reports (the script also writes `evidence: <id>` to `jira-comments.txt`). A `REFUSED` from the script is a finding: the evidence is missing or stale.
   - **The build changes after review** (a fix, or a split at step 9): re-run the gate, then run `loop-evidence.js <KEY> --verdict <V> --post` yourself; it edits the same evidence comment.
9. **If BLOCK:** treat it as STUCK (step 7), including the findings. For a narrow block on one isolated line or file, offer the reviewer's two options: make it safe, or split it into its own change. To split: `svn revert` that file only if the change is its only difference from the baseline, otherwise remove just that hunk. The server may still have it.
10. **Otherwise write `.loop/<KEY>/checkin.md`** for the manual check-in:
    - An **explicit-path** `svn commit` of exactly the ticket's files (`svn status` minus `svn-baseline.txt` minus `.loop/`). Never a whole-tree commit: the working copy holds unrelated changes, unversioned harness output and possibly a cookie file.
    - Any `svn add` still needed, and whether the source copies are included: docs `*_Map_Spec.xls`, and template duplicates such as `solution/templates/`.
    - Whether to commit `e2sc-ui_tests/`, `tests/locked/<KEY>/` (specs and pages), `tests/ui-contract.ts` and `tests/logic/<KEY>/` (the Logic harness and its `sources.txt`). If yes, a selective add plus `svn:ignore` for `node_modules`, `test-results`, `playwright-report` and `recordings`. Never commit staged copies of the code under test or `.loop/<KEY>/last-logic.out`.
    - **If `e2sc-ui_tests/` is not under version control** (`svn info e2sc-ui_tests` fails), say so in `checkin.md`: the locked tests and Logic harness are not preserved by the code commit. Offer a copy of `tests/locked/<KEY>/` and `tests/logic/<KEY>/` into a versioned place, the suggested location being `solution/project/ssp-ext/E2/test/loop/<KEY>/` (check it is versioned, or give the `svn add` for its parent), with the exact `svn add` and `svn commit` lines. Never copy `node_modules`, `test-results`, `recordings` or `tests/_probe/`. Without a copy, the hashes in `.loop/<KEY>/ui.locked` (and the sha256 on Jira) are the only record.
    - A commit message starting `<KEY>:`, in plain ASCII (an en dash from the Jira title gets garbled in svn).
    - A summary: the change, criteria-to-tests mapping, verification results (yours and the implementer's), iteration count, any healings (from `healing.log`), the review verdict and notes, and what is still deployed on the server, including anything split out.
11. **Post a Jira comment** with the change summary, the criterion-by-criterion result and the review verdict, pointing to the test-evidence comment for the per-test results (don't repeat them). Don't transition the ticket: it stays in "Fix Required" until the user moves it after check-in.
12. **Write `.loop/<KEY>/run-summary.json`:** ticket, outcome, first_pass, iterations, healings, failing_tests (counts per test), review_verdict, files_changed, jira_comments (including `evidence`), ui_locked_sha256.
13. **Hand over.** Tell the user it's ready to check in and point to `checkin.md`, with the follow-ups: manual checks for paths the tests don't cover, split-out changes, server clean-up (`*.bak.<KEY>`, `/tmp/<KEY>/`, and the Logic run folder `/tmp/loop-logic-<user>/<KEY>/` on the Logic host), deleting any cookie file in the repo, and, if the tests weren't copied into a versioned place, that the lock hashes are the only record of them. Once they've committed, check `svn log -v` shows exactly the intended files and record the revision in `run-summary.json`. Remind them to start the next ticket in a new session or after `/clear`, and to keep unrelated work out of the loop session.

## Contract change
When the user decides the contract changes (on a CONTRACT_GAP, a CONTRACT_MISMATCH, or a later decision):
1. The user states the new contract. Update `intake.md`, `test-cases.md`, `cases.approved` (its frozen sections) and the cases Jira comment. Rename an open `contract-mismatch.md` to `contract-mismatch-<n>.md`.
2. Ask the user to delete `.loop/<KEY>/ui.locked` and `ui.bound` (and `healing.log`) themselves: the hook blocks every agent from touching them. If a **Logic** case changed, they also delete `logic.locked`.
3. Re-run step 2b (ui-assert rewrites the specs and interface; the UNBOUND run; the lock; a new sha256 on Jira). If a Logic case changed, re-run step 2a: the rewritten harness must go RED again (use `LOGIC_SRC_ROOT` with the pre-change revision once the code exists) before `--logic --lock`. If no Logic case changed, run the locked Logic harness (`loop-verify.sh`) to confirm it still holds.
4. The implementer fixes the build to the new contract (step 3), then test-author binds again (step 4).
