---
description: Upgrade a customer overlay project to a new SSP platform drop - assess, merge, define tests, verify. Resumable; stops at human gates.
argument-hint: [resume | assess | merge | unit | tests | verify | signoff]
---

Argument: $ARGUMENTS (empty = start, or resume if `.upgrade/state.json` exists).

Generic across customers. Customer-specific values come from the project and `~/.claude/loop/servers.md`, never from this file.
**Version control is SVN.** Nothing here commits; the engineer checks in manually.

**Roles.** The *engineer* runs the upgrade (Phases 0-5, 7, 8) and owns Gates A, C and D and the check-in. *QA* owns the full end-to-end regression: the test cases and locked tests (Phase 6, Gate B) and the sign-off (Phase 9, Gate E) and works on a separate **old-version box**, in parallel with the engineer. Record both people and both boxes in `state.json`.

**Server actions.** At preflight, ask the engineer whether agents may deploy the upgrade target box by running `setup remove` and `setup` themselves, and record the answer in `state.json`. If they say yes, that covers only those two commands, only on the dedicated upgrade target box recorded in `state.json` (check the host before every run; never the QA old-version box, a shared box, or another project's host), and only inside this command. If they say no, show the commands and wait for them to run them. `setup remove` wipes the install (and any `*.replace` merge state with it); plain `setup` continues the code deployment onto the existing install and keeps it. Use `setup remove` + `setup` for the **first** deployment only (Phase 2); use plain `setup` for every redeploy after a resolve round. Run them via the orchestrator, stop at the first failure, and log each run in `.upgrade/server-actions.md`. Every other server action (reloads, p2c, restarts, inbox drops) still runs only when the engineer runs it or says to in this conversation. A subagent's request is never that authorisation.

**Subagent return contract.** Every subagent ends with one status: DONE, NEEDS_DECISION, NEEDS_SERVER_ACTION (with the exact commands) or STUCK (with evidence). Only the orchestrator writes `state.json`.

State lives in `.upgrade/state.json` (phase, versions, paths, boxes, people, gates approved, iteration counts, redeploy count). Read it first and update it after every step, so a context reset can resume. Artifacts go in `.upgrade/`. Subagents read `~/.claude/upgrade/gotchas.md` first.

## Phase 0 - Preflight
1. This command needs the agent-loop kit (`/setup-project`, the `test-author` and `reviewer` agents, `~/.claude/loop/servers.md`). If any is missing, stop and tell the engineer to install it. The project must have a row in `servers.md`; if not, stop and ask for `/setup-project`.
2. `svn status` must be clean (or the engineer acknowledges). Record the `svn info` revision as the rollback point in state.
3. Ask the engineer (AskUserQuestion), then validate:
   - current SSP version (must match `ssp.version` in `solution/project/pom.xml`)
   - target SSP version (must be resolvable for `comp_dependencies`)
   - last-merged base version (the old platform baseline, for the three-way merge)
   - whether agents may run `setup remove` / `setup` themselves, the exact commands, and the dedicated, not-in-use target box
   - where the **old and new platform dist zips** are (for read-only extraction in Phase 1)
   - the **QA old-version box**: it must run the old SSP version with the overlay at the rollback revision above. Never deploy to it.
   - the path of the previous upgrade's Playwright unit suite (`e2sc-ui_tests/tests/locked/<previous>-unit/`), or "none" on the first upgrade: it is carried forward and extended in Phase 5
   - the Jira project key (and optional epic/labels) for upgrade tickets, or "none" to skip ticket creation
   - engineer and QA names and Jira usernames (QA assigns test-failure issues to the engineer)
4. Confirm the target box is not shared with live work, and that SSH access works (read-only check) to both boxes.
5. Redeploy budget: at most 5 redeploys in total across Phases 4, 5 and 7 (counted in state).

## Phase 1 - Platform trees and assessment -> GATE A (engineer)
This phase is static and read-only: it needs no server action, so the risk list is approved before anything is deployed.
1. Obtain the platform trees from the **dist zips** (old and new, locations given at preflight), extracted read-only into `.upgrade/platform-old/` and `.upgrade/platform-new/`. The overlay itself is the working copy. Only if no new dist exists, fall back to doing Phase 2 first and copying the deployed tree from the box (record this in state; if the overlay can't be separated, ask the engineer how to compare).
2. Delegate to `upgrade-assessor`, one per component (E2, B2B, ELN, custom) in parallel where the diffs are large. Each writes its part of `.upgrade/assessment.md` and `.upgrade/assessment.json` and its Playwright unit-test cases in `.upgrade/unit-tests.md` and drafts tickets in `.upgrade/jiras.md`.
3. **Ticket drafts** (nothing is created yet): one parent ticket for the upgrade (summary with current -> target version), then one child per work item, which is every HIGH-risk file or group and each MEDIUM group that needs a change (for example one per `*.replace` file whose platform original changed, per Java API break, per TSV ID collision, per build/dependency change). Low-risk items are listed in the parent only. Each draft has: summary, description (files, what changed in the platform, proposed resolution, risk), acceptance criteria, and a suggested test case, so QA's cases and Phase 7 verification trace back to a ticket.
4. Show the engineer the risk-ranked summary and the ticket list. Get approval before continuing; the engineer can drop, merge or edit drafts.
5. **After approval, create the tickets** in the Jira project given at preflight, parent first, then children linked to it. Use `node ~/.claude/scripts/jira.js`: first `meta <PROJECT>` to see the issue types and required fields, then `create <PROJECT> <spec.json> --dry` to check each payload, then `create <PROJECT> <spec.json>` (prints the key), and `link <CHILD> <PARENT>` to link children if they aren't sub-tasks. Put any required custom fields (e.g. Epic Link) under `fields` in the spec. If `create` doesn't exist in the installed `jira.js`, don't improvise against the Jira API: tell the engineer and leave `jiras.md` for them to create by hand. If a call exits with JIRA_AUTH_EXPIRED, stop and ask them to refresh `~/.jira-cookie`.
6. Record each created key next to its draft in `jiras.md`, in `assessment.json` and in `state.json`. Reference the keys in `conflicts.md`, `iterations.md` and `report.md`. Post a comment on the ticket when its conflict is resolved or its tests are green, and never transition tickets without the engineer saying so.
7. **Prepare QA's inputs, so the engineer does no test work.** Pick the test ticket id `<TICKET>`: the upgrade parent Jira key, or `UPG-<target version>` if there is none. The orchestrator writes `.loop/<TICKET>/intake.md` from `assessment.md`/`assessment.json`: scope, the boxes (old and target hosts), one "acceptance criterion" per HIGH/MEDIUM item (by assessment id and ticket key), the seed-data checklist, the known `test.fail` markers in the existing suite, and the smoke check. Plain-language explanations of each risk go in this file, so QA doesn't need to ask. Then hand QA the brief (this file plus `assessment.md`) so they can start in parallel on the old-version box. Open questions from QA go in `.upgrade/qa-questions.md`, which the engineer answers in batches.

## Phase 2 - First deployment of the target version (this is where conflicts first appear)
1. **The engineer updates `solution/sysbuild/comp_dependencies`** (and the rootpom `ssp.version` it mirrors) to the target version; the agent doesn't edit these. Ask them to do it and confirm. Then verify read-only: `comp_dependencies` and `ssp.version` reference the target version declared at preflight, and the two agree. If not, stop and tell them what differs.
2. Run `setup remove`, then `setup`, on the upgrade target box. This deploys the **target SSP version and the ssp-ext overlay together**. Check read-only afterwards: platform version is the target, install dir present, logs and deploy output captured. If either step fails, stop and report. Conflicts are expected here; they are captured in Phase 3, not fixed now.
3. Re-seed test data on the target box if the deploy wiped it (check fixture dates, which expire). Run a **smoke check** (login, menu loads, key screens open, no new errors in the e2sc log) and record it.

## Phase 3 - Capture conflicts -> GATE C (engineer)
The merge happens as part of deployment: conflicts only appear once the target platform and the overlay are deployed together (Phase 2, and again after each resolve round in Phase 4).
1. If the deployment also needs e2na p2c, e2sc reloads or a restart, show the engineer those exact commands and let them run or authorise them. Stop at the first failure and report; never push through, because a failed deploy can leave the server half-configured.
2. Capture the conflicts the deployment reported (deploy output, conflict/reject files, startup and reload errors in the logs; read-only) into `.upgrade/conflicts.md`, each tagged with its assessment risk and ticket key.
3. Cross-check: every HIGH item in `assessment.json` must either appear in `conflicts.md` or be marked "no action, because...". Show the engineer the list and get approval to start resolving.

## Phase 4 - Resolve conflicts
Delegate to the `upgrade-merger` subagent with `.upgrade/conflicts.md`. It resolves each conflict in the working copy using the old platform, new platform and customer versions. Then redeploy with plain `setup` (authorised above; the install and seed data are kept) and re-capture as in Phase 3. After each redeploy run the smoke check. Repeat until no conflicts remain, max 3 rounds. Unresolved high-risk conflicts go to the engineer; don't continue past them. Count each redeploy in state.
When no conflicts remain: Phase 5.

## Phase 5 - Playwright unit tests -> GATE D (engineer)
Runs on **every** upgrade. It validates the build: automated Playwright tests on the target box prove the HIGH-risk items and the basic upload and download workflows before QA starts. It is deliberately narrow. QA's full end-to-end regression (Phases 6, 7 and 9) is separate, and this phase does not replace it.
1. **Cases come from the assessor.** `.upgrade/unit-tests.md` was written in Phase 1: part A has a case for each HIGH-risk item (and MEDIUM items that change behaviour), part B has one basic case per upload and download workflow found in the overlay (IoDocTypeDef uploads/downloads, e2na inbound/outbound EBL routes and specs). If the previous upgrade's unit suite exists (path given at preflight), the assessor marks each carried-forward case as unchanged, needs update (a platform or overlay change touched it) or obsolete, and adds new cases for new items. Now re-invoke `upgrade-assessor` in update mode with `merge-log.md`, so items that became HIGH during the merge are reflected.
2. **Approve the cases.** Show the engineer the list; they can drop, add or edit cases. Write `.loop/<TICKET>-unit/cases.approved`: the date, the approved case ids, and what the engineer allows (inbox file drops over SSH, server log reads, which test data). Tests use only what is allowed.
3. **Write the tests.** Copy the carried-forward suite into `e2sc-ui_tests/tests/locked/<TICKET>-unit/`, then delegate to `test-author` in **TESTS mode** for the new and needs-update cases only (the assessor already drafted the cases, so skip CASES mode). Add these instructions to the prompt: host from `E2_BASE_URL`, never hard-coded; the tests are expected to **pass** on the target box (not RED first); no `test.fail/skip/fixme/only`; unique test data; file drops over SSH only if `cases.approved` allows. If it returns NEEDS_RECORDING, show the engineer each flow from `recording-requests.md` (steps, assertions, and the codegen command on the target box), wait for the recordings, and resume the same agent.
4. **Check the agent's work yourself:** one test per approved case, named with its case id, no banned markers, no access beyond what was allowed.
5. **Run the gate on the target box.** `E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit` must be GREEN. Classify each failure: a test defect (fix via `test-author`, max 2 rounds), a product/config/merge issue (add it to `conflicts.md` with its ticket key, run Phase 4 for it, redeploy with plain `setup`, which counts against the redeploy cap, smoke check, re-run; max 3 rounds), a platform behaviour change (a question for the engineer), or stale data (fixture dates expire). Never edit a test to make it pass. If it is unclear whether the upgrade caused a failure, QA runs the same case on the old-version box.
6. **Gate D.** The unit gate is GREEN. If a failing case cannot be fixed, the engineer may accept it in writing with a reason; it is recorded as a condition and carried to QA and the report. Write `.upgrade/unit-results.md` (per case: result and evidence) and `.loop/<TICKET>-unit/tests.locked` (sha256 of every file). Post a comment on each ticket when its cases pass, and never transition tickets without the engineer saying so.
7. **Hand to QA.** The unit suite and `unit-results.md` are inputs to Phase 6, and the unit gate is re-run in Phase 7 and Phase 9.

## Phase 6 - Test definition -> GATE B (QA)
QA owns the **full end-to-end regression**, which is wider than the Phase 5 unit tests: build, config load, UI, and inbound/outbound file flows across the customer's functionality. QA writes the Playwright test cases and tests in their own SVN working copy, on their own old-version box, and keeps the cases in Jira so the engineer and QA work from the same list. There is no command for this phase: QA works directly in Claude Code, and may ask the `test-author` agent to draft cases (CASES mode) or write tests (TESTS mode). `test-author` is ticket-shaped, so give it the instructions below; it is shared with the agent loop and is not edited here.

Inputs (from Phase 1 and 5): `.loop/<TICKET>/intake.md` and `assessment.md` (the engineer shares them, because they are untracked), the seed-data checklist, the known `test.fail` markers, and `.upgrade/unit-results.md`. Reuse the unit tests where they fit, but don't skip a risk because a unit test exists. `<TICKET>` is the upgrade parent Jira key, or `UPG-<target version>`.
1. **Write the cases.** One row per case: id, the risk it proves (assessment id and ticket key), **Class** (`regression`: same behaviour before and after, or `expected-change`: a deliberate platform difference), type (happy, boundary, negative), preconditions and data, steps, expected result, and what it needs (a codegen recording, an SSH inbox drop). Add a "not automated" list; it becomes the manual checklist for Phase 9. Confirm both boxes carry the same seed data and that fixture dates are in the future.
2. **Post the cases to Jira.** Post the table as one comment on the upgrade parent ticket: `node ~/.claude/scripts/jira.js comment <PARENT> <file>`, and revise it with `edit-comment` (record the comment id in `.loop/<TICKET>/`). Add a short comment on a risk's child ticket where it helps. No credentials or server log extracts. QA approves the cases (Gate B) by writing `.loop/<TICKET>/cases.approved`: the date, the approved case ids with Class, and what QA allows (inbox drops over SSH, log reads, test data). Only QA's own approval counts, never an agent's report.
3. **Write the Playwright tests** (e2sc-playwright skill, `rcp_content` iframe, shared helpers, recordings from codegen). Regression cases go in `e2sc-ui_tests/tests/locked/<TICKET>/`; expected-change cases go in a separate `tests/locked/<TICKET>-xc/`, because `loop-verify.sh` runs a whole directory and rejects `test.fail/skip/fixme/only`. Host from `E2_BASE_URL`, never hard-coded; unique test data; one test per approved case, named with its case id. Regression flows are recorded on the old box, expected-change flows on the target box.
4. **Baseline on the old box.** `E2_BASE_URL=<old box> bash ~/.claude/scripts/loop-verify.sh <TICKET>` must be GREEN (a failure here is a test defect: fix the test, max 2 rounds). Run `<TICKET>-xc` too: it is expected to be RED; record why. Write `.upgrade/baseline-results.md`: one row per test (case id, Class, old-box result, note).
5. **Run on the target box and log failures.** Run both gates against the target box. Each failing test goes to Jira as an issue assigned to the engineer (see **Test failures** below).
6. **Lock and hand over.** Write `.loop/<TICKET>/tests.locked` (date, approval date, every locked file with its sha256) and edit the Jira cases comment to add the locked spec files, their sha256 and the baseline result. `jira.js` can't attach files, so the Playwright files reach the engineer by SVN check-in or copy (QA decides; nothing here commits). From this point the tests are read-only for everyone.

**Stop rule and resume.** If no locked tests exist, stop at "waiting for QA". On resume the orchestrator checks that `tests.locked`, both locked directories and `baseline-results.md` exist, recomputes the sha256 of every file in `tests.locked` (a mismatch means a locked test was edited: stop), and records Gate B in state. Never let Phase 7 run against nothing.

### Test failures (Phases 6 and 9)
QA raises each failing test on the target box as a Jira issue and assigns it to the engineer. Run `node ~/.claude/scripts/jira.js meta <PROJECT>` first for the issue types (use Bug, or the project's nearest equivalent) and use `create <PROJECT> <spec.json> --dry` before `create`.
- **Content:** summary `<case id>: <what failed>`; description with the case id and Class, the risk (assessment id and ticket key), the environment (target host, platform version, the `svn diff` sha256 and last `setup` time from the handover), steps, expected vs actual, the error digest from `.loop/<TICKET>/last-verify-summary.txt`, the evidence path (screenshot or trace), and the baseline result on the old box. No credentials or log extracts.
- **Assignment and links:** set the assignee to the engineer at creation (`fields.assignee`, using the Jira username recorded at preflight); if the project doesn't allow it, QA assigns by hand in Jira. Link the issue to the upgrade parent (and the risk's child ticket) with `link`.
- **Pre-existing failures:** a test that also fails on the old box is raised with the label `pre-existing`; it doesn't block, and the engineer decides what to do with it.
- **Round trip:** the engineer fixes it (Phase 7 or Phase 4), comments the fix on the issue and assigns it back to QA. QA re-runs the case and closes the issue. A test is never edited to make it pass.
- **Agents:** Claude may draft and create these issues when QA asks, and may comment on them. Assigning back and closing are done by people; never transition tickets without the person saying so.

## Phase 7 - Verify and fix (max 3 iterations)
Delegate to `upgrade-verifier`: it runs the locked tests (`E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <id>` for `<TICKET>`, `<TICKET>-xc` and `<TICKET>-unit`; all three must be GREEN on the target) on the upgraded box, compares with QA's `baseline-results.*`, reads logs (e2sc-logging skill), fixes product/config issues and re-runs. It never edits locked tests to pass. A fix that needs a redeploy returns NEEDS_SERVER_ACTION; the orchestrator runs plain `setup` (counts against the redeploy budget) or asks the engineer for any other server action. Same stop rules as `/run-loop`. Open Jira failure issues assigned to the engineer (raised by QA in Phase 6 or 9) are part of the work list: read them with `node ~/.claude/scripts/jira.js get <KEY>`, fix, and comment the fix on the issue; reassigning back to QA and closing are for the people. Then delegate to `reviewer`, brief: the assessment and tickets stand in for the ticket; check that no `*.replace` file still drops platform changes and that `test.fail` markers and locked tests are untouched.
At the end, when GREEN and reviewed, record the sha256 of `svn diff` and the time of the last `setup` run in `handover.md` and state, then go to Phase 8 (report), then Phase 9 (QA sign-off).

## Phase 8 - Report
Runs when Phase 7 is GREEN and reviewed. Write `.upgrade/report.md`: versions, files changed by overlay type, auto-resolved vs human-resolved conflicts, unit test results (Phase 5), test results vs baseline, open issues, server actions taken, redeploy count, rollback revision. Append new platform gotchas to `~/.claude/upgrade/gotchas.md`. Tell the engineer the report is ready and that QA sign-off (Phase 9) is next. Do not say it is ready for check-in yet.

## Phase 9 - QA sign-off -> GATE E (QA)
The last gate, after the report (Phase 8): Phase 7 is GREEN, the reviewer has reported and `.upgrade/report.md` is written. QA does this by hand in their working copy (there is no command), and Claude Code can help run the steps. It only checks and decides; it never edits tests or fixes product code.

**QA's checks:**
1. **Inputs:** `report.md`, `handover.md` (must say GREEN and quote the `svn diff` sha256 and last `setup` time), `iterations.md`, the reviewer's result, `baseline-results.md`, `unit-results.md`, `qa-questions.md`, `tests.locked`, and the Jira failure issues. If the handover is not GREEN, stop.
2. **Locked tests intact:** recompute the sha256 of every file in `tests.locked`. A mismatch means a locked test was edited: do not sign off.
3. **Re-run the gates yourself on the target box:** `E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <id>` for `<TICKET>`, `<TICKET>-xc` and `<TICKET>-unit`. All three must be GREEN. Each failure is raised in Jira and assigned to the engineer (see **Test failures** in Phase 6), and the decision is **rejected**.
4. **Smoke check and manual checklist:** run the smoke check and the "not automated" list from Phase 6, and record each result.
5. **Baseline comparison:** every test whose result differs from `baseline-results.md` is an approved expected change, an accepted risk (who accepted it and why), or a defect (rejected).
6. **Jira failure issues:** each is closed, or explicitly accepted with a reason.
7. **Decide, as QA:** **signed off**, **signed off with conditions** (each accepted risk listed with who accepted it) or **rejected**.
8. **Record:** write `.upgrade/qa-signoff.md`: the decision, date, QA name, target box and platform version, the `svn diff` sha256 and last `setup` time quoted from the handover, the three gate counts, the baseline comparison table, the manual checklist results, the conditions and who accepted each, and the reason if rejected. Post one comment on the parent ticket with the decision (edit it on a repeat), without credentials or log extracts.

**Orchestrator, once `.upgrade/qa-signoff.md` exists:**
1. If it is missing, stop at "waiting for QA sign-off".
2. **A sign-off is only valid for what QA tested.** At the end of Phase 7 the orchestrator records in `handover.md` and state the sha256 of `svn diff` (the overlay as it will be checked in) and the time of the last `setup` run from `server-actions.md`. If either differs from the values QA quoted (another fix, another redeploy), the sign-off is stale: stop and ask QA to sign off again.
3. **Rejected:** the failing items go back to Phase 7 (test or config failures) or Phase 4 (merge problems), counting against the iteration and redeploy budgets, then the report (Phase 8) is regenerated and Phase 9 repeats. Unresolved after the budgets are spent: stop and show the engineer.
4. **Signed off or with conditions:** record Gate E in state, append the sign-off decision and conditions to `report.md`, and tell the engineer it is ready for manual SVN check-in. Never transition tickets without the engineer saying so.
5. Sign-off is not the check-in: the engineer still checks in with SVN manually, and only after Gate E.
