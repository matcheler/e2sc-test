---
description: Step 1 of 3 of an SSP upgrade - preflight, assessment, unit tests written and locked on the current version, version files and the Bamboo build. Nothing touches the target box. Resumable; stops at human gates.
argument-hint: <JIRA-KEY|none> [resume]
---

Arguments: $ARGUMENTS. The first word is the upgrade's Jira key (a ticket the engineer created) or `none`; an optional second word `resume`. Without `resume`, start a new upgrade, or resume if `.upgrade/state.json` exists. Handle the key first, as "The Jira key argument" in rules.md says (parse, check, compare with state).

This is the first of the three upgrade commands: `/upgrade-prepare` (this one, Phases 0-2 and Phase 3 steps 1-2), then `/upgrade-deploy`, then `/upgrade-validate`. **Read `~/.claude/upgrade/rules.md` first**: the roles, the two boxes, the server-action rules, the subagent return contract, the `state.json` fields and the budgets are defined there and apply here. If it is missing, stop and tell the engineer to reinstall the kit. Nothing in this command touches the target box: the deploy is `/upgrade-deploy`.

**Resume.** If `.upgrade/state.json` exists, read it and skip what is done: preflight recorded means Phase 1 (if the merged assessment exists but `assessmentReport` isn't in state, resume at step 4); Gate A recorded means Phase 2 and Phase 3 steps 1-2; Gate B recorded and the suite locked (`unitSuiteLocked`) means only the version files and the build may be left; all of those plus a green Bamboo build means this command is finished (tell the engineer to run `/clear`, then `/upgrade-deploy <KEY>`). If `state.json` shows a later phase, say which command owns it (see rules.md) and stop.

## Phase 0 - Preflight
1. This command needs the agent-loop kit (`/setup-project`, `loop-verify.sh`, `loop-record.js`, the `e2sc-ui_tests` harness template, `~/.claude/loop/servers.md`). If any is missing, stop and tell the engineer to install it. The project must have a row in `servers.md`; if not, stop and ask for `/setup-project`.
2. `svn status` must be clean (or the engineer acknowledges). Record the `svn info` revision as the rollback point in state.
3. Ask the engineer (AskUserQuestion), then validate:
   - current SSP version (must match `ssp.version` in `solution/project/pom.xml`)
   - target SSP version (must be resolvable for `comp_dependencies`)
   - last-merged base version (the old platform baseline, for the three-way merge)
   - whether agents may run `setup remove` / `setup` themselves, the exact `setup remove` / `setup` commands, and the dedicated, not-in-use target box (the `setup migrate` commands are not asked now: the engineer gives them during the setup in `/upgrade-deploy`)
   - the **baseline box**: the host that runs the current version, for writing and proving the unit tests in Phase 2. It must not be the target box. Confirm it is not shared and what tests may do there (create data, drop inbox files; the standing answer is yes to both)
   - where the **old and new platform dist zips** are (for read-only extraction in Phase 1)
   - the **Confluence release page** for the target stream (for 26.x: `https://confluence.dev.e2open.com/display/RelMGMT/Solutions+Releases+26.x`): Phase 1 reads the release notes and the build number there
   - the **Bamboo plan** that builds the overlay for this upgrade, and whether to use a project update script instead of editing the version files by hand (`solution/sysbuild/tools/update*.sh`). `comp_dependencies` and `pom.xml` are always checked in by the engineer before the build (the kit never commits)
   - the path of the previous upgrade's Playwright unit suite (`e2sc-ui_tests/tests/locked/<previous>-unit/`), or "none" on the first upgrade: it is carried forward and extended in Phase 2
   - engineer and QA names
4. Confirm the target box is not shared with live work, and that SSH access works to both boxes (read-only checks). Check read-only that the baseline box runs the current version; if it doesn't, stop and ask.
5. Write `state.json` with the fields in rules.md and the budgets, including `jiraKey` from the argument. `authorisation` records whether the engineer authorised `setup remove` / `setup` and the `setup migrate` commands on the target box, with the box and the date; `/upgrade-deploy` and `/upgrade-validate` read it before any deploy or redeploy.

## Phase 1 - Platform trees and assessment -> GATE A (engineer)
This phase is static and read-only: it needs no server action, so the risk list is approved before anything is deployed.
1. Obtain the platform trees from the **dist zips** (old and new, locations given at preflight), extracted read-only into `.upgrade/platform-old/` and `.upgrade/platform-new/`. The overlay itself is the working copy. If no new dist exists, stop and ask the engineer: the fallback is to deploy first (`/upgrade-deploy`) and copy the deployed tree from the box, which means the tests in Phase 2 are written after the deploy; record that choice in state.
2. **Release notes from Confluence.** Read the release page for the target SSP version, read-only, with `node ~/.claude/scripts/confluence.js` (it uses `~/.confluence-cookie`). Start from the release page given at preflight (for 26.x: `https://confluence.dev.e2open.com/display/RelMGMT/Solutions+Releases+26.x`): `children` or `find` locates the release for the target version, then `details <page>` and `get <page>` read it. From the Release details table take the **Build Numbers** (mandatory, for example `ssp261rel1044`), the Build Date, the Release Date and the Customers, and from the page the release scope and any migration notes. Write `.upgrade/release-info.md` (the page URL, those fields, the scope and the notes) and record `releaseBuild` in state. If the page can't be found, more than one release matches the target version, or the Build Numbers cell is empty, stop and ask the engineer: never guess a build number. If the script is missing, or a call exits with CONFLUENCE_AUTH_EXPIRED, ask the engineer to refresh `~/.confluence-cookie`, or to paste the Release details table.
3. Delegate to `upgrade-assessor`, one per component (E2, B2B, ELN, custom) in parallel where the diffs are large, each reading `.upgrade/release-info.md` for the release scope and migration notes. Each writes only under `.upgrade/assessment/<component>/` (`assessment.md`, `assessment.json`), with every id prefixed by the component (`E2-001`), so parallel runs never overwrite each other; a project with no components uses `all`. Then the orchestrator merges them: concatenate into `.upgrade/assessment.md` and `.upgrade/assessment.json`, and check every id is unique. The assessment id is the reference for each item from here on (in `conflicts.md`, `merge-log.md`, `iterations.md`, the reports): no Jira tickets are created or drafted (rules.md). Then add a **Release build** section at the top of `.upgrade/assessment.md` from `release-info.md`: the build number, the source page, the build and release dates, the customers, the release scope and migration notes, and the proposed edits (old -> new) to `solution/sysbuild/comp_dependencies` and to `ssp.version` in `solution/project/pom.xml`, following their existing format. Mark any value you can't derive from the build number "to confirm", and ask about it at Gate A.
4. **Assessment report (HTML).** Build `.upgrade/assessment-report.html` from the merged `assessment.md`, `assessment.json` and `release-info.md`, following the shared-report rules in rules.md. Contents:
   - header: current -> target version, release build number, date
   - risk counts (HIGH / MEDIUM / LOW) per component and in total
   - the Release build section: build and release dates, release scope and migration notes, and the proposed `comp_dependencies` and `pom.xml` edits (old -> new), with any "to confirm" values highlighted
   - table of **HIGH and MEDIUM items** (id, component, file, overlay type, what changed in the platform, proposed resolution, suggested test)
   - the items whose tests are **deferred to Phase 6** (screen or behaviour changed by the new platform), with the reason
   - the LOW items, in a collapsed `<details>` section
   No ticket list and no ticket drafts. Publish it as a private Artifact and record `assessmentReport` (path and URL) in state.
5. Show the engineer the assessment report link, the risk-ranked summary, and the Release build section with the proposed `comp_dependencies` and `pom.xml` edits. Also list the HIGH and MEDIUM items whose screen, field, route, spec or behaviour the new platform changes (from the assessment and the release notes): their cases can't be written on the old version and Phase 2 defers them to Phase 6. The upgrade is expected to be as-is, so if there are more than a few, say so: the engineer may decide to write more of the suite on the target box. Get approval before continuing; the engineer can drop, merge or edit items. Record Gate A in state.
6. If the engineer edited the assessment at Gate A, update `assessment.md` and `assessment.json`, rebuild `assessment-report.html` and re-publish it to the same URL (`assessmentReport` in state). Then attach the approved `assessment-report.html` to `jiraKey` (`node ~/.claude/scripts/jira-attach.js <KEY> .upgrade/assessment-report.html assessment-report-<yyyy-mm-dd>.html`; skipped when the key is `none`), and record the attachment id in state (`assessmentReport`, `jiraWrites`). If the report changes again later, attach the new version too (rules.md).
7. **Pick the test id.** `<TICKET>` is the test id: `UPG-<target version>`. Record it in state (`ticket`); an upgrade resumed with a `ticket` already in state keeps it, so the locked suite path still resolves. The unit suite uses `<TICKET>-unit`; `/upgrade-deploy` and `/upgrade-validate` read the id from state, so they take no key. Give the engineer the approved assessment report link (`assessmentReport`) to pass to QA so they can plan their end-to-end regression; don't share it yourself.

## Phase 2 - Unit cases and Playwright tests on the baseline box -> GATE B (engineer)
Runs on **every** upgrade, after Gate A and before the deploy. The cases come from the assessment alone, and the tests are written, recorded and proven on the baseline box (the current version), then locked. The upgrade is expected to be as-is, so the same suite should pass on the target box in Phase 6; a failure there is a finding, not a test to fix. It is deliberately narrow: automated tests that prove the HIGH-risk items and the basic upload and download workflows. QA's full end-to-end regression is separate and outside this toolkit, and this phase does not replace it.

**Order with Phase 3 steps 1-2.** Start Phase 3 steps 1-2 (below: version files, the engineer's check-in, the Bamboo build) right after Gate A, and run this phase while waiting for the check-in and the build.

**No discovery in this phase.** Every screen a test needs comes from a human Playwright codegen recording on the baseline box, or from a recording that already exists. Never run the discovery replay subagent here, and don't let the test author explore a screen or write trial specs.

1. **Draft the cases.** Delegate to `upgrade-test-author` in **CASES mode**. It reads only the approved assessment (`assessment.md`, `assessment.json` with each item's `suggestedTest`, `release-info.md`), the previous upgrade's suite if one exists (path given at preflight), and the overlay; there is no merge yet, so nothing can shape the cases. It writes `.upgrade/unit-tests.md`: part A has a case for each HIGH-risk item (and MEDIUM items that change behaviour), part B has one basic case per upload and download workflow found in the overlay (IoDocTypeDef uploads/downloads, e2na inbound/outbound EBL routes and specs), trimmed to the smallest set that proves each item, with a Level, a Status (carry-forward) and a Timing per case (`write now`, or `deferred` with the platform change that makes it untestable on the old version), a "not covered" list and questions. It writes no code and touches no server in this mode.
2. **Gate B: approve the cases.** Show the engineer the table, the deferred cases, the "not covered" list and the agent's questions; they can drop, add or edit cases, or move a case between `write now` and `deferred`. Write `.loop/<TICKET>-unit/cases.approved`: a Gate B section with the date, the approved case ids and their Timing, and what the engineer allows on the baseline box (inbox file drops over SSH, data creation, server log reads, which test data). Record Gate B in state. Then comment the approved cases on `jiraKey` in plain text (rules.md, "Plain-text case comments": Parts A and B, deferred cases marked, the "not covered" list), from `.upgrade/jira-comment-gate-b.txt` with `node ~/.claude/scripts/jira.js comment <KEY> .upgrade/jira-comment-gate-b.txt`, and record the comment id in `jiraWrites` (skipped when the key is `none`). If the engineer later amends Gate B, comment the amended cases the same way.
3. **Write the tests from recordings.** Copy the carried-forward suite into `e2sc-ui_tests/tests/locked/<TICKET>-unit/`, and the previous upgrade's recordings (`e2sc-ui_tests/recordings/<previous>-unit/`, if they exist) into `recordings/<TICKET>-unit/`. Set `E2_BASE_URL` to the **baseline box** in the environment, then delegate to `upgrade-test-author` in **TESTS mode**, box `baseline`, case set Gate B `write now`. It reuses the recordings it finds (`recordings/INDEX.md`, the copied recordings) and requests a recording for every workflow that has none.
   - **NEEDS_RECORDING:** show the engineer each flow from `.loop/<TICKET>-unit/recording-requests.md`: the cases it supports, the steps to click through (which record or data to use, and where to stop: on the result screen, with an assertion), and the command, run from `e2sc-ui_tests/` with `E2_BASE_URL` set to the baseline box: `node ~/.claude/scripts/loop-record.js <TICKET>-unit <flow>` (or `npx playwright codegen --output recordings/<TICKET>-unit/<flow>.ts <baseline box>/e2sc/logon.do`). Stop at "waiting for recordings" until the engineer says they are done, then resume the same agent. If a recording stops short (for example at a popup), ask for a follow-up recording that continues from there; never fill the gap with a replay.
   - **NEEDS_DISCOVERY** is not allowed in this phase: resume the agent and tell it to turn each screen into a recording request.
   - **CONTRACT_MISMATCH:** the baseline box differs from the approved case. Show the engineer `contract-mismatch.md`; they edit the case (an amendment to Gate B in `cases.approved`) or drop it.
4. **Check the agent's work yourself:** one test per approved `write now` case, named with its case id, no banned markers, no hard-coded host, no access beyond what was allowed, every test built from a recording (none from guessed selectors), and `.upgrade/unit-plan.md` accounts for every approved case. New recordings have a row in `recordings/INDEX.md`.
5. **Prove the suite on the baseline box.** `E2_BASE_URL=<baseline box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit` must end GREEN. The test author has already fixed test defects (max 2 rounds); on the old version a failure is never an upgrade finding, so one that is left means the case, the recording or the data is wrong: show it to the engineer, who re-records, edits the case or drops it. Never weaken an assertion to get green.
6. **Lock.** Write `.loop/<TICKET>-unit/tests.locked` (sha256 of every file in `e2sc-ui_tests/tests/locked/<TICKET>-unit/`) and `.upgrade/baseline-results.md` (per case: the result on the baseline box and the evidence). Record `unitSuiteLocked` and `baselineResults` in state. From here the tests are only changed through a re-entry approved by the engineer (Phase 7).

## Phase 3, steps 1-2 - Version files and the Bamboo build
The rest of Phase 3 (the deploy) is in `/upgrade-deploy`.
1. **Update the version files.** The orchestrator edits `solution/sysbuild/comp_dependencies` and the `ssp.version` in `solution/project/pom.xml` to the build and version approved at Gate A (the assessment's Release build section), following their existing format and touching nothing else. If the engineer named the project's own update script at preflight (`solution/sysbuild/tools/update*.sh`; these files carry an "Auto updated" stamp), use it instead of editing by hand. Show `svn diff` for the two files (the engineer checks them in in step 2). Then verify read-only that both reference the target and agree with each other. If the mapping from the build number is unclear, or they don't agree, stop and ask.
2. **Prompt the engineer to check in the version files, then run the Bamboo build.** Bamboo builds from the repository, so `comp_dependencies` and `pom.xml` must be checked in first, and only the engineer does that (the kit never commits). Tell them to check in just those two files with SVN, and stop at "waiting for the check-in" until they say it is done; record the revision in state (`versionFilesRevision`, from `svn info`). Then prompt them to kick off the Bamboo build (the plan from preflight, and the build to expect), and stop at "waiting for the Bamboo build" until they say it finished. Record the result (green or red, and the build number) in state. If it is red, stop and ask the engineer what to do: never deploy a red build. While waiting for either, run Phase 2 if it isn't locked yet.

## Done
When Gate B is recorded, the Phase 2 suite is locked and the Bamboo build is green, record the phase in state and tell the engineer: run `/clear`, then `/upgrade-deploy <KEY>` to deploy the target version onto the target box.
