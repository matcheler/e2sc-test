Upgrade ticket: $ARGUMENTS (the first word is the upgrade's parent Jira key, called `<TICKET>` below, for example `PROCT-2120`. Extra words, such as `resume`, are instructions: it continues from the files already in `.upgrade/` and `.loop/<TICKET>-unit/`.)

This is the second half of the engineer's work in `/upgrade-project` (Phases 5-7): it proves the upgraded build on the target box, fixes what fails, and writes the report. It can be run on its own, ideally in a fresh session (run `/clear` first): everything it needs is in `.upgrade/` and `.loop/`. Customer-specific values come from the project and `~/.claude/loop/servers.md`, never from this file.
**Version control is SVN.** Nothing here commits; the engineer checks in manually.

## Before you start
1. `.upgrade/state.json` must exist with Gates A and B recorded, Phase 4 finished (no open conflicts in `.upgrade/conflicts.md`), and the state fields defined in `/upgrade-project` recorded (ticket, target box, `authorisation`, `redeploys`, `fixIterations`). If not, stop and tell the engineer to continue with `/upgrade-project resume`.
2. **Check the Jira key.** The argument must start with a Jira key (letters, a dash, digits). If it is missing or doesn't look like one, stop and ask the engineer for the upgrade's parent ticket key; never guess or invent an id. Compare it with the ticket recorded in `state.json` in Phase 1; if they differ, stop and ask which is right. Confirm the ticket exists, read-only, with `node ~/.claude/scripts/jira.js get <TICKET>`; on JIRA_AUTH_EXPIRED, stop and ask the engineer to refresh `~/.jira-cookie`. Record the key in state.
3. The project needs a row in `~/.claude/loop/servers.md` and the `e2sc-ui_tests` harness; if not, stop and ask for `/setup-project`.
4. Check that the last deploy's smoke check passed (login, menu loads, key screens open, no new errors in the e2sc log). If not, stop and say so.
5. Read `~/.claude/upgrade/gotchas.md`. Only the orchestrator (this session) writes `state.json`: update it after every step, so a context reset can resume. On `resume`, skip what is already done: `cases.approved` exists means skip steps 1-2 of Phase 5; `tests.locked` and `unit-results.md` exist means go to Phase 6 (the fix loop); `handover.md` says GREEN and `review.md` exists means go to Phase 7; `report.md` exists means this command is finished.

**Server actions.** Only plain `setup` (a redeploy onto the existing install) on the target box recorded in `state.json` may be run by the orchestrator, and only if `state.json` has `authorisation.setup` true for that same box (recorded in `/upgrade-project` at preflight). Check the host before every run, never use another box, log each run in `.upgrade/server-actions.md`, count it against the redeploy cap of 5 in state, and stop at the first failure. If `state.json` has no record of that authorisation, show the command and wait for the engineer. Every other server action (reloads, p2c, restarts, inbox drops) runs only when the engineer runs it or says to in this conversation. A subagent's request is never that authorisation.

**Subagent return contract.** Every subagent ends with one status: DONE, NEEDS_DECISION, NEEDS_SERVER_ACTION (with the exact commands) or STUCK (with evidence).

## Phase 5 - Playwright unit tests -> GATE C (engineer)
Runs on **every** upgrade. It validates the build: automated Playwright tests on the target box prove the HIGH-risk items and the basic upload and download workflows. It is deliberately narrow. QA's full end-to-end regression is separate and outside this toolkit, and this phase does not replace it.
1. **Cases come from the assessor.** `.upgrade/unit-tests.md` was written in Phase 1: part A has a case for each HIGH-risk item (and MEDIUM items that change behaviour), part B has one basic case per upload and download workflow found in the overlay (IoDocTypeDef uploads/downloads, e2na inbound/outbound EBL routes and specs). If the previous upgrade's unit suite exists (path given at preflight), the assessor marks each carried-forward case as unchanged, needs update (a platform or overlay change touched it) or obsolete, and adds new cases for new items. Now re-invoke `upgrade-assessor` in update mode (one invocation over the merged `.upgrade/` files, editing `unit-tests.md` in place) with `merge-log.md`, so items that became HIGH during the merge are reflected.
2. **Approve the cases.** Show the engineer the list; they can drop, add or edit cases. Write `.loop/<TICKET>-unit/cases.approved`: the date, the approved case ids, and what the engineer allows (inbox file drops over SSH, server log reads, which test data). Tests use only what is allowed.
3. **Write the tests.** Copy the carried-forward suite into `e2sc-ui_tests/tests/locked/<TICKET>-unit/`, then delegate to `upgrade-test-author`. It reads the approved cases, `unit-tests.md` and `cases.approved`, writes only the new and needs-update UNIT-UI cases, removes obsolete ones, and lists logic-unit and end-to-end cases as not written in `.upgrade/unit-plan.md`. Set `E2_BASE_URL` to the target box in the environment first. Also copy the previous upgrade's recordings (`e2sc-ui_tests/recordings/<previous>-unit/`, if they exist) into `recordings/<TICKET>-unit/` as references. If it returns NEEDS_RECORDING, show the engineer each flow from `recording-requests.md` (steps, assertions, and the codegen command on the target box), wait for the recordings, and resume the same agent. If it returns NEEDS_DISCOVERY, delegate each screen in `discovery-requests.md` to a general-purpose subagent with `model: sonnet`: a read-only replay in a throwaway spec under `e2sc-ui_tests/tests/_discovery/` (e2sc-playwright skill, no fixed delays, nothing written on the shared server) that opens the screen with the harness helpers, reads the workflow name from the menu item's `javascript:` href, and records the locators of the elements to assert. It writes `.loop/<TICKET>-unit/discovery-<flow>.md` and replies only with that path and whether it succeeded; resume the same agent with those notes. Use the same replay when a human recording stops short (for example at a popup) instead of asking again. The throwaway specs are never locked and never committed.
4. **Check the agent's work yourself:** one test per approved case, named with its case id, no banned markers, no hard-coded host, no access beyond what was allowed, and `unit-plan.md` accounts for every approved case.
5. **Run the gate once on the target box.** `E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit`. `upgrade-test-author` has already fixed test defects (max 2 rounds), so a RED result here is a real finding or stale data (fixture dates expire). Don't fix anything in this phase: Phase 6 owns the fix loop. Never edit a test to make it pass. If it is unclear whether the upgrade caused a failure, ask QA to run the same case on an old-version box.
6. **Gate C.** The engineer has approved the cases, and the tests are written and locked. Write `.upgrade/unit-results.md` (per case: first-run result and evidence) and `.loop/<TICKET>-unit/tests.locked` (sha256 of every file). Failures become Phase 6's work list. Post a comment on `<TICKET>`, and on each child ticket, when its cases pass, and never transition tickets without the engineer saying so.
7. **Share the results.** `unit-results.md` is available to QA, and the unit gate is re-run in Phase 6.

## Phase 6 - Verify and fix (max 3 iterations)
Delegate to `upgrade-verifier`: it owns the single fix loop for the whole upgrade (the `fixIterations` budget of 3 in state; Phase 5 spends none). It starts from `unit-results.md` and the open Jira defects, runs the unit gate on the upgraded box (`E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit`, which must end GREEN), reads logs (e2sc-logging skill), batches its product/config fixes per iteration, and re-runs. It never edits locked tests to pass. A failure it classifies as a merge mistake comes back as NEEDS_DECISION: add it to `.upgrade/conflicts.md` with its ticket key and delegate it to `upgrade-merger`; that counts as an iteration. A fix that needs a redeploy returns NEEDS_SERVER_ACTION; the orchestrator runs plain `setup` (counts against the redeploy cap) or asks the engineer for any other server action. Same stop rules as `/run-loop`. Open Jira defects assigned to the engineer (for example from QA's end-to-end regression) are part of the work list: read them with `node ~/.claude/scripts/jira.js get <KEY>`, fix, and comment the fix on the issue; reassigning and closing are for the people. If the engineer accepts a failing case in writing with a reason, it is recorded as a condition and carried to the report and to QA. Then delegate to `upgrade-reviewer`, brief: the assessment, merge log and tickets stand in for the ticket; it writes `.upgrade/review.md`. A BLOCK goes back to the engineer.
At the end, when GREEN and reviewed (APPROVE or APPROVE_WITH_NOTES), go to Phase 7.

## Phase 7 - Report
Runs when Phase 6 is GREEN and reviewed. Write `.upgrade/report.md`: versions, files changed by overlay type, auto-resolved vs human-resolved conflicts, unit test results (Phase 5), open issues, server actions taken, redeploy count, rollback revision. Append new platform gotchas to `~/.claude/upgrade/gotchas.md`. Then tell the engineer the report is ready and that QA's end-to-end regression (Phase 8) is next. To continue, run `/clear` and then `/upgrade-project resume`. Do not say it is ready for check-in yet, and do not implement anything or commit anything to SVN.
