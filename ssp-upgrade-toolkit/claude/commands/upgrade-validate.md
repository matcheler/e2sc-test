argument-hint: <JIRA-KEY|none> [resume]

Arguments: $ARGUMENTS. The first word is the upgrade's Jira key (the one given to `/upgrade-prepare`) or `none`; an optional second word `resume`. Either way, continue from the files already in `.upgrade/` and `.loop/<TICKET>-unit/`. `<TICKET>` is the test id that `/upgrade-prepare` recorded in `state.json` in Phase 1; it is not the Jira key.

This is the last of the three upgrade commands: `/upgrade-prepare`, then `/upgrade-deploy`, then `/upgrade-validate` (this one, Phases 6-9): it adds the cases the merge exposed, runs the unit suite (written and locked on the baseline box in Phase 2) on the target box, fixes what fails, writes the report, and after the check-in works QA's defects. **Read `~/.claude/upgrade/rules.md` first**: the roles, the two boxes, the server-action rules, the subagent return contract, the `state.json` fields and the budgets are defined there and apply here. If it is missing, stop and tell the engineer to reinstall the kit. Ideally run it in a fresh session (run `/clear` first): everything it needs is in `.upgrade/` and `.loop/`.

## Before you start
0. **The Jira key.** Handle the key argument as "The Jira key argument" in rules.md says: parse it, check it with `jira.js get` (unless `none`), and compare it with `jiraKey` in state; stop if it is missing or differs.
1. `.upgrade/state.json` must exist with Gates A, B and C recorded, the Phase 2 suite locked (`unitSuiteLocked` in state, `.loop/<TICKET>-unit/tests.locked` and `cases.approved` with a Gate B section), Phase 5 finished (no open conflicts in `.upgrade/conflicts.md`), and the state fields defined in rules.md recorded (ticket, target box, `authorisation`, `redeploys`, `fixIterations`, `reentries`). If not, stop and tell the engineer to continue with `/upgrade-deploy <KEY> resume` (or `/upgrade-prepare <KEY> resume` if Gate B isn't recorded). Exception: if state records Gate B as "skipped: upgrade predates Phase 2", there is no Phase 2 suite, and Phase 6 drafts and writes every case on the target box (see Phase 6).
2. **Read the test id.** `<TICKET>` is `ticket` in `state.json`. If it is missing, stop and tell the engineer to continue with `/upgrade-prepare <KEY> resume`, which records it. Never ask for one or invent one.
3. The project needs a row in `~/.claude/loop/servers.md` and the `e2sc-ui_tests` harness; if not, stop and ask for `/setup-project`.
4. Check that the last deploy's smoke check passed (login, menu loads, key screens open, no new errors in the e2sc log). If not, stop and say so.
5. Read `~/.claude/upgrade/gotchas.md`. Only the orchestrator (this session) writes `state.json`: update it after every step, so a context reset can resume. On `resume`, skip what is already done: `unit-tests.md` has a Part C section but `cases.approved` has no Gate D section means skip step 1 of Phase 6 (unless the engineer asks to redraft); a Gate D section means skip steps 1-2; Gate D recorded "nothing to add" means go to step 5; `tests.locked` re-written after Gate D and `unit-results.md` exist means go to Phase 7 (the fix loop); `handover.md` says GREEN and `review.md` exists means go to Phase 8; `report.md` exists means go to Phase 9 (first confirm Gate E: see Phase 9); Phase 9 done means this command is finished.

**Server actions.** Only plain `setup` (a redeploy onto the existing install) on the target box recorded in `state.json` may be run by the orchestrator, and only if `state.json` has `authorisation.setup` true for that same box (recorded by `/upgrade-prepare` at preflight). Check the host before every run, never use another box, log each run in `.upgrade/server-actions.md`, count it against the redeploy cap of 5 in state, and stop at the first failure. If `state.json` has no record of that authorisation, show the command and wait for the engineer. Every other server action (reloads, p2c, restarts, inbox drops other than those the approved tests make) runs only when the engineer runs it or says to in this conversation. A subagent's request is never that authorisation.

## Phase 6 - Merge cases and first run on the target box -> GATE D (engineer)
The Phase 2 suite was written from the assessment and proven on the baseline box. This phase adds only what the merge brought to light, then runs the whole suite on the target box once. It is deliberately narrow; QA's full end-to-end regression is separate and outside this toolkit.
1. **Draft the merge cases.** Delegate to `upgrade-test-author` in **CASES-DELTA mode**. It reads the final `assessment.json`, `merge-log.md` (including the FIX-NEEDED entries) and `conflicts.md`, plus `unit-tests.md` and `cases.approved` from Phase 2. It appends to `unit-tests.md`: Part C, a case for each conflict that needed the engineer's decision and each merge marked uncertain; Part D, one entry per FIX-NEEDED item with its likely cause, a proposed scope (in or out of the upgrade) and a case for the in-scope ones; the Phase 2 `deferred` cases, now to be written on the target box; and `needs change` or `moot` marks (with the reason) on approved cases the merge affected. It never drops an approved case. If Gate B was skipped (an upgrade that predates Phase 2), it drafts Parts A and B as well, from the assessment.
2. **Gate D: approve the cases and triage the FIX-NEEDED items.** Show the engineer the new cases, the marks, the FIX-NEEDED list, the "not covered" list and the questions. They approve, edit or drop cases (only the engineer removes a `moot` case), and decide each FIX-NEEDED item:
   - **in scope** (caused by the merge or the new platform): fixed in this upgrade; record it in state (`fixNeeded`) and in Part D of `unit-tests.md`, and keep its case;
   - **out of scope** (already broken before the upgrade): not fixed here; record it in state and Part D, list it in the report for the engineer to follow up, and drop its case, unless the engineer pulls the item into the upgrade.
   No Jira tickets are created or drafted for either (rules.md).
   Append a Gate D section to `.loop/<TICKET>-unit/cases.approved`: the date, the approved case ids, the FIX-NEEDED decisions, and what the engineer allows on the target box. Record Gate D in state. Then comment the Gate D cases on `jiraKey` in plain text (rules.md, "Plain-text case comments": Part C, Part D with each FIX-NEEDED decision, the deferred cases now written, and the `needs change` / `moot` marks), from `.upgrade/jira-comment-gate-d.txt` with `node ~/.claude/scripts/jira.js comment <KEY> .upgrade/jira-comment-gate-d.txt`, and record the comment id in `jiraWrites` (skipped when the key is `none`, or when Gate D is "nothing to add"). If there is nothing to add (no Part C, no deferred case, no FIX-NEEDED item, no mark), record Gate D as "nothing to add" and go to step 5.
3. **Write the new tests on the target box.** Set `E2_BASE_URL` to the target box in the environment, then delegate to `upgrade-test-author` in **TESTS mode**, box `target`, case set Gate D. It writes the approved Part C, Part D and deferred cases and updates the `needs change` ones, in `e2sc-ui_tests/tests/locked/<TICKET>-unit/`; it doesn't touch the Phase 2 tests otherwise.
   - **NEEDS_RECORDING:** show the engineer each flow from `recording-requests.md` (steps, assertions, and the codegen command on the target box), wait for the recordings, and resume the same agent.
   - **NEEDS_DISCOVERY** (allowed in this phase): delegate each screen in `discovery-requests.md` to a general-purpose subagent with `model: sonnet`: a read-only replay in a throwaway spec under `e2sc-ui_tests/tests/_discovery/` (e2sc-playwright skill, no fixed delays, nothing written on the shared server) that opens the screen with the harness helpers, reads the workflow name from the menu item's `javascript:` href, and records the locators of the elements to assert. It writes `.loop/<TICKET>-unit/discovery-<flow>.md` and replies only with that path and whether it succeeded; resume the same agent with those notes. Use the same replay when a human recording stops short (for example at a popup) instead of asking again. The throwaway specs are never locked and never committed.
   - **Red first.** A test for an in-scope FIX-NEEDED item whose fix is not in yet must fail on the target box, for the reason its case states: that proves it catches the problem. If it passes, it doesn't discriminate: the test author reworks it (within its 2 rounds) or reports it. A test for a fix the merge already made can't be shown red; its case must state the discriminating check, and `upgrade-reviewer` checks it.
4. **Check the agent's work yourself:** one test per approved case, named with its case id, no banned markers, no hard-coded host, no access beyond what was allowed, the Phase 2 tests unchanged apart from approved `needs change` cases, the red-first results recorded, and `unit-plan.md` accounts for every approved case.
5. **Lock.** Re-write `.loop/<TICKET>-unit/tests.locked` with the sha256 of every file in the suite (Phase 2 and Phase 6 tests). Any later change goes through a re-entry (Phase 7).
6. **Run the whole suite once on the target box.** `E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit`. Don't fix anything in this phase: Phase 7 owns the fix loop. Never edit a test to make it pass. Red-first tests are expected to fail. Any other failure is a real finding, stale data (fixture dates expire), or a platform difference the verifier classifies in Phase 7. If it is unclear whether the upgrade caused a failure, ask QA to run the same case on an old-version box.
7. **Record the results.** Write `.upgrade/unit-results.md`: per case, the first-run result on the target box, the evidence, and the baseline result from `baseline-results.md`. Failures become Phase 7's work list. `unit-results.md` is available to QA.

## Phase 7 - Verify and fix (max 3 iterations)
Delegate to `upgrade-verifier`: it owns the single fix loop for the whole upgrade (the `fixIterations` budget of 3 in state; Phase 6 spends none). It starts from `unit-results.md`, the in-scope FIX-NEEDED items and the open Jira defects, runs the unit gate on the upgraded box (`E2_BASE_URL=<target box> bash ~/.claude/scripts/loop-verify.sh <TICKET>-unit`, which must end GREEN), reads logs (e2sc-logging skill), batches its product/config fixes per iteration, and re-runs. It never edits locked tests to pass. A failure it classifies as a merge mistake comes back as NEEDS_DECISION: add it to `.upgrade/conflicts.md` with its assessment id and delegate it to `upgrade-merger`; that counts as an iteration. A fix that needs a redeploy returns NEEDS_SERVER_ACTION; the orchestrator runs plain `setup` (counts against the redeploy cap) or asks the engineer for any other server action. Same stop rules as `/run-loop`. Open Jira defects assigned to the engineer (for example from QA's end-to-end regression) are part of the work list: read them with `node ~/.claude/scripts/jira.js get <KEY>`, fix, and comment the fix on the issue; reassigning and closing are for the people. If the engineer accepts a failing case in writing with a reason, it is recorded as a condition and carried to the report and to QA.

**Re-entry to Phase 2 (a platform difference on one case).** The suite was written on the old version, so a slight difference on the target box (a field in another place or control, or a behaviour change the release notes name) can fail a test whose behaviour is fine. The verifier never touches the test: it lists each such case in `iterations.md` as a **platform difference**, with its evidence (the baseline result from `baseline-results.md`, what the target box shows, and the release note or assessment line if there is one), and returns NEEDS_DECISION. The engineer decides per case:
- **re-record** (selectors only; the assertion stays the same),
- **amend the case** (the expected result changes; needs a release note or assessment reference), or
- **reject** (it is a regression: it stays in the fix loop).
For a re-record or an amendment, append the decision to `cases.approved` (an amendment also updates the row in `unit-tests.md`), set `E2_BASE_URL` to the target box, and delegate to `upgrade-test-author` in **TESTS mode**, box `target`, case set that case only, re-entry. Handle NEEDS_RECORDING and NEEDS_DISCOVERY as in Phase 6 step 3. Then re-write `tests.locked` and log each change in `.upgrade/test-changes.md`: case id, re-record or amendment, the reason, the evidence, the old and new assertion, the engineer's approval and date. For each **amendment** (not a re-record: that changes only selectors), comment the amended case on `jiraKey` in plain text (`Amended case - <date>`: the case block with the old and new expected result and the reason), from `.upgrade/jira-comment-amend-<case id>.txt`, and record the comment id in `jiraWrites`. Budgets: re-records are free; each batch of amendments counts as one iteration of `fixIterations` (or `qaFixIterations` after the check-in). Count re-entered cases in `reentries`: above 3, stop and tell the engineer the upgrade isn't as-is; they decide whether to redo the affected cases together through Phase 6 steps 1-5.

Then delegate to `upgrade-reviewer`, brief: the assessment and merge log stand in for a ticket, and it also checks `test-changes.md`, the red-first evidence and the FIX-NEEDED scope; it writes `.upgrade/review.md`. A BLOCK goes back to the engineer.
At the end, when GREEN and reviewed (APPROVE or APPROVE_WITH_NOTES), go to Phase 8.

## Phase 8 - Report -> GATE E (engineer: review, then check in)
Runs when Phase 7 is GREEN and reviewed. Write `.upgrade/report.md`: versions, files changed by overlay type, auto-resolved vs human-resolved conflicts, unit test results (the baseline results from Phase 2 and the target results from Phases 6-7), re-entries from `test-changes.md`, each FIX-NEEDED item (fixed, out of scope for the engineer to follow up, or accepted by the engineer with the reason), open issues, server actions taken, redeploy count, rollback revision, links to the two shared reports (`assessmentReport` and `conflictReport` in state: the local path, the Artifact URL and the Jira attachment ids of each, where they exist), and the Jira key with each attachment and comment made on it (`jiraWrites`). Append new platform gotchas to `~/.claude/upgrade/gotchas.md`. Then tell the engineer the report is ready: review `.upgrade/report.md` and `.upgrade/review.md`, then check in with SVN manually (Gate E). The kit never commits, so do not implement anything or commit anything to SVN. QA's end-to-end regression (Phase 9) follows the check-in; to track it, run `/clear` and then `/upgrade-validate <KEY> resume`.

## Phase 9 - QA end-to-end regression (after the check-in)
The last step. It starts once the engineer has reviewed the report and checked in (Phase 8, Gate E). QA runs the full end-to-end regression on the upgraded target box, in their own process and outside this toolkit. QA raises a Jira defect for each failure, assigned to the engineer, and shares the test results. On `resume` after Phase 8, first ask the engineer to confirm they reviewed the report and checked in, and record Gate E in state, with the revision they checked in (from `svn info`) as `checkInRevision`. Then:
1. **Wait for the results.** Stop at "waiting for QA results" until the engineer gives the location or link of QA's test results. Record it in state (`qaResults`) and in `report.md`.
2. **Work the defects.** The engineer gives the keys of the open QA defects (or reads them with `node ~/.claude/scripts/jira.js get <KEY>`). List them in `report.md`. Each is fixed through Phase 7 (config or product failures) or by `upgrade-merger` (merge problems), counting against the `qaFixIterations` budget of 3 (not the pre-check-in budget) and the redeploy cap, and reviewed again by `upgrade-reviewer` against `checkInRevision`. The fix is commented on the issue, and the engineer assigns it back to QA, who retests and closes it. The fixes come after the check-in, so the engineer checks them in with SVN as a follow-up.
3. **Done.** QA's results are shared and no open QA defects remain assigned to the engineer, or the engineer accepts the remaining ones in writing with a reason (each becomes a condition in the report). Record the results reference, the defect list and any conditions in `report.md`. Never create, reassign or transition Jira issues; commenting the fix on QA's defects is the only Jira write.
