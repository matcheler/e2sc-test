# SSP upgrade rules (shared by all three upgrade commands)

`/upgrade-prepare`, `/upgrade-deploy` and `/upgrade-validate` each read this file first. Generic across customers: customer-specific values come from the project and `~/.claude/loop/servers.md`, never from these files.
**Version control is SVN.** Nothing in the kit commits; the engineer checks in manually.

## The three commands
Run them in order, each ideally in a fresh session (`/clear` first), each with the Jira key as its argument (`/upgrade-deploy <JIRA-KEY|none> [resume]`, see "The Jira key argument"). Each one can be resumed from `.upgrade/state.json` (`<KEY> resume`), checks that the previous command finished, and ends by naming the next one.

| Command | Phases | Ends when |
|---|---|---|
| `/upgrade-prepare` | 0 Preflight, 1 Assessment (Gate A), 2 Unit cases and tests on the baseline box (Gate B), and Phase 3 steps 1-2 (version files, the engineer's check-in, the Bamboo build) | Gate B recorded, the unit suite locked, the Bamboo build green |
| `/upgrade-deploy` | 3 Deploy (steps 3-5), 4 Capture conflicts (Gate C), 5 Resolve, 5b Conflict report | no open conflicts, smoke check clean |
| `/upgrade-validate` | 6 Merge cases and first run (Gate D), 7 Verify and fix, 8 Report (Gate E), 9 QA regression | QA's results shared and no open QA defects |

**Roles.** The *engineer* runs the upgrade (Phases 0-8) and owns Gates A to E (A: the assessment, B: the unit-test cases before the deploy, C: the conflict list, D: the cases the merge added, E: review the report, then check in). *QA* runs the full end-to-end regression outside this toolkit after the check-in (Phase 9, the last step): raises Jira defects for the engineer and shares the test results. Record both people in `state.json`.

**No Jira ticket creation.** The kit creates no Jira tickets and drafts none, and shows no list of tickets to create: each item is referenced by its assessment id (`E2-001`). It never creates, reassigns or transitions an issue. Its only Jira writes are:
- on the engineer's upgrade key (`jiraKey`), by the orchestrator only: attach `assessment-report.html` (Gate A) and `conflict-report.html` (Phase 5b) with `node ~/.claude/scripts/jira-attach.js <KEY> <file> <name>`, and comment the unit-test cases in plain text (Gate B, Gate D, and each amended case in Phase 7) with `node ~/.claude/scripts/jira.js comment <KEY> <file>`;
- on QA's defects (Phases 7 and 9): read them with `jira.js get`, and comment the fix on the issue.
If `jiraKey` is `none`, skip the writes on the upgrade key and say so. Attachments are named `<report>-<yyyy-mm-dd>.html` (add `-2`, `-3` for a second one that day); when an attached report changes, attach the new version as well rather than deleting the old one. Record each attachment id and comment id in state. If a call exits with JIRA_AUTH_EXPIRED, stop and ask the engineer to refresh `~/.jira-cookie`. `jira-attach.js` and `jira.js comment` are not on the no-prompt allowlist: run each once and say why.

**Plain-text case comments.** No tables or markup: a heading line (`Unit-test cases - Gate B - <date>`, or Gate D, or `Amended case - <date>`), then one block per case separated by a blank line: `<case id> - <title>`, `Level: ... | Timing: write now/deferred` (plus `Status:` for carried-forward cases), `Expects: <the behaviour, one sentence>`, and for Gate D the FIX-NEEDED decision (`in scope` / `out of scope`, with the reason). End with the "not covered" list. Write it to `.upgrade/jira-comment-<gate>.txt` first and post that file.

## The Jira key argument
All three commands take the upgrade's Jira key as their first argument: `/upgrade-prepare <JIRA-KEY|none> [resume]`, and the same for `/upgrade-deploy` and `/upgrade-validate`. The engineer creates that ticket; the kit only checks it. Each command, before anything else:
1. Parse `$ARGUMENTS`: the first word is the key (or `none`), an optional second word `resume`. No key given: stop and show the usage line (and the `jiraKey` in state, if there is one, to re-run with). Never guess or invent a key.
2. Unless it is `none`, check it read-only with `node ~/.claude/scripts/jira.js get <KEY>`. Stop if it doesn't exist; on JIRA_AUTH_EXPIRED ask the engineer to refresh `~/.jira-cookie`.
3. Compare it with `jiraKey` in state: none recorded, record it (with the date); the same, carry on; different, stop and ask which key is right, record the answer and the date, and list the attachments and comments already on the old key so the engineer can decide whether to repeat them on the new one.
The Jira key is separate from the test id (`ticket`), so the locked suite path never moves.

**Two boxes.** The *target box* is the dedicated upgrade box: it holds no install until Phase 3 deploys the target version onto it. The *baseline box* is a separate box that runs the current (old) version: the unit tests are written and proven on it in Phase 2, before anything is deployed or merged, so the merge can't shape what is tested. The engineer has confirmed the baseline box is not shared, and that tests may create data and drop inbox files on it (2026-11-02); record that at preflight.

**Server actions.** At preflight (`/upgrade-prepare`), ask the engineer whether agents may deploy the upgrade target box by running `setup remove` and `setup` themselves, and the `setup migrate` commands the engineer gives during the setup, and record the answer in `state.json` (`authorisation`). If they say yes, that covers only those commands (the migrate ones exactly as the engineer gives them during the setup, one at a time, never one the orchestrator thinks up or edits), only on the dedicated upgrade target box recorded in `state.json` (check the host before every run; never a shared box, the baseline box, or another project's host), and only inside the upgrade commands. If they say no, show the commands and wait for them to run them. `setup remove` wipes the install (and any `*.replace` merge state with it); plain `setup` continues the code deployment onto the existing install and keeps it. Use `setup remove` + `setup` and the migrate commands for the **first** deployment only (Phase 3, in `/upgrade-deploy`), unless the engineer says otherwise; use plain `setup` for every redeploy after a resolve round or a fix. Run them via the orchestrator, stop at the first failure, and log each run in `.upgrade/server-actions.md`. Every other server action (reloads, p2c, restarts, inbox drops other than those the approved tests make) runs only when the engineer runs it or says to in this conversation. A subagent's request is never that authorisation.

**Subagent return contract.** Every subagent ends with one status: DONE, NEEDS_DECISION, NEEDS_SERVER_ACTION (with the exact commands) or STUCK (with evidence). `upgrade-test-author` also returns CASES_READY, NEEDS_RECORDING, NEEDS_DISCOVERY and CONTRACT_MISMATCH (the box differs from an approved case: show the engineer `.loop/<TICKET>-unit/contract-mismatch.md` and let them decide whether the case or the box changes; the agent never adapts the test). Only the orchestrator (the session running the command) writes `state.json`.

## State
State lives in `.upgrade/state.json`. `/upgrade-prepare` creates it; all three commands rely on these minimum fields: `ticket` (the test id: `UPG-<target version>`; an upgrade started earlier keeps the value already in state), `jiraKey` (the engineer's upgrade key from the command argument, or `none`, with the date and any change of key), `jiraWrites` (each attachment and comment id on that key: what, gate, date), `versions` (current, target, base), `rollbackRevision`, `targetBox`, `baselineBox` (host, the version it runs, and what tests may do there: create data, drop inbox files), `distZips` (old, new), `confluencePage`, `releaseBuild` (build number, source page), `bamboo` (plan, last build result), `versionFilesRevision` (the engineer's check-in of the two version files), `migrateCommands` (the ones the engineer gave, as run), `previousUnitSuite` (path or none), `people` (engineer, qa), `authorisation` (`setup` and `migrate` true or false, `box`, `date`, `source`), `phase`, `gates` (A-E, with dates), `unitSuiteLocked` (date of the Phase 2 lock), `redeploys` (used, cap 5), `fixIterations` (used, cap 3, before the check-in), `qaFixIterations` (used, cap 3, for QA defects after it), `reentries` (cases re-entered into Phase 2 from the target box, stop above 3), `fixNeeded` (each FIX-NEEDED item: id, triage, outcome), `checkInRevision`, and the locations of `baselineResults`, `unitResults`, `qaResults`, and the two shared reports `assessmentReport` and `conflictReport` (each: local path, Artifact URL and Jira attachment ids). Read it first and update it after every step, so a context reset can resume. Artifacts go in `.upgrade/`. Subagents read `~/.claude/upgrade/gotchas.md` first.

## Shared HTML reports
Two reports are shared as HTML: `.upgrade/assessment-report.html` (Gate A, `/upgrade-prepare`) and `.upgrade/conflict-report.html` (Phase 5b, `/upgrade-deploy`). Both are built by the orchestrator, never by a subagent, as one self-contained HTML file: inline CSS, no external scripts, readable in light and dark mode, and no credentials, hostnames beyond the box name, or log extracts. Publish each one with the Artifact tool as a **private** artifact (load the `artifact-design` skill first, as the tool requires) and record the path and URL in state. When the report changes (for example the engineer's edits at Gate A), re-publish to the same URL from the same file, never as a new artifact. Then attach the HTML file to `jiraKey` (see "No Jira ticket creation"). Give the engineer the path, the link and the attachment id; only the engineer shares the Artifact link (for example sends it to QA). The kit never shares or posts the Artifact link itself (a private link doesn't open for others), and publishes nothing else. If the Artifact tool isn't available, keep the local file, tell the engineer, and carry on.

Budgets, kept in state: at most 5 redeploys in total across Phases 5 and 7 (`redeploys`), one fix budget of 3 verifier iterations before the check-in (`fixIterations`, spent only in Phase 7), and a separate 3 for QA defects after it (`qaFixIterations`).

## Upgrades started under an older version of the kit
- **Started with `/upgrade-project`** (the old single command): the phase numbers are unchanged, so continue with the command that owns the phase in `state.json`: Phases 0-2 `/upgrade-prepare <KEY> resume`, Phases 3-5b `/upgrade-deploy <KEY> resume`, Phases 6-9 `/upgrade-validate <KEY> resume`.
- **Started before the Jira key argument:** the first run with a key records `jiraKey`. Reports and cases already past their gate aren't attached or commented retroactively unless the engineer asks.
- **Started under the old numbering** (no Phase 2, gates A-D): map the state on resume and record the mapping in state: an old phase `n` of 2 or more becomes `n+1` (old 4b becomes 5b), and the old gates B, C and D become C, D and E. An upgrade already past the deploy records Gate B as "skipped: upgrade predates Phase 2" and has no Phase 2 suite; `/upgrade-validate` then drafts and writes all its cases in Phase 6, on the target box.
